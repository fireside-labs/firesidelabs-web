GGUF Identity Verification

A Note on Identity Verification in the GGUF Ecosystem

In the open-source LLM ecosystem, models are distributed as GGUF files (quantized, local-inference-optimized formats). You download a file named experimental-graft-v1.gguf and assume it's a custom variant. Sometimes it's not. Sometimes it's the unmodified base model with a new filename.

We benchmarked three models with different names, ran experiments thinking we were testing novel architectures, and published results that were meaningless. They were all the same file.

The Discovery

We maintained a suite of Llama-3.1-8B variants with custom configurations. Three files existed:

1. llama-3.1-8b-instruct-q4_k_m.gguf (explicit base model)
2. experimental-graft-v1.gguf (claimed to be a layer-grafted variant)
3. validated-graft-v2.gguf (claimed to be an improved, validated variant)

We benchmarked all three. Results were puzzling: identical scores on every benchmark, identical per-question latency. Investigation revealed the cause: the surgery script had failed silently. No layers were modified. The filenames were updated. The file contents were not.

SHA256 verification confirmed: all three hashes were identical. We had benchmarked the same model three times under different names.

Why This Happened

Most GGUF files are generated automatically via quantization scripts. If the script has a bug, or if the input weights weren't actually modified, you end up with a GGUF that claims to be a variant but is identical to the base. Most creators don't verify this. They assume the script did its job.

Why GGUF Identity is Fragile

The Problem

GGUF metadata includes fields like general.name, general.architecture, and general.quantization_version. But it does NOT include:

• surgery.lineage—what modifications were made
• surgery.base_hash—SHA256 of the original model
• surgery.timestamp—when modifications happened
• surgery.author—source/origin

Without this information, you can't distinguish a genuinely custom model from a mislabeled base model.

Detection Methods

Method 1: Full File SHA256

Definitive but slow. For 100GB+ files, takes minutes.

Method 2: Partial Hash

Fast. Compute SHA256 of first 64MB. Catches ~99% of duplicates in seconds.

Method 3: Metadata Inspection

Fast but not definitive. Metadata can be forged, and modified models often keep original metadata.

Recommended Approach

(1) Compare GGUF metadata (fast, catches obvious mismatches). (2) Compare partial SHA256 of first 64MB (catches duplicates in seconds). (3) If suspicious, compare full file SHA256 (definitive, slow).

The Broader Ecosystem Problem

The open GGUF ecosystem has exploded. Hugging Face, GitHub, Discord servers, personal websites all distribute GGUFs. In a benchmark suite of 100 models, you might have:

• 10 genuinely unique models
• 30 variants of a few base models
• 60 duplicates or near-duplicates

Your benchmark results are inflated. You think you've tested 100 models when you've tested 10.

Best Practices

For Model Creators

1. Verify Your Model Changed. Before distributing, compute SHA256. If it matches the base, something went wrong.

2. Include Metadata. Mark as modified or not. Include base model SHA256 if modified.

3. Use Clear Naming. Name variants to describe the modification. Not experimental-graft-v1 (which says nothing about what's inside). Use llama-3.1-8b-qwen3-graft-L18-26 (clear: Llama base, Qwen graft at layers 18-26).

For Benchmark Builders

1. Hash All Models on Intake. Compute SHA256 when you download. Store in a manifest.

2. Audit Existing Suite. Check for duplicates. You may have far fewer unique models than you think.

3. Include Hash in Metadata. Every benchmark result should reference the model's SHA256. If someone else gets a different result with the same filename, they can immediately check: "Do our hashes match?"

The GGUF ecosystem lacks standardized identity verification. Until the spec extends with provenance tracking, teams must hash models on intake, detect duplicates, and store hashes alongside results.

Future: Proposed Extension

The GGUF spec should include surgery.* metadata fields:

surgery.is_modified: true surgery.base_model_name: "llama-3.1-8b-instruct" surgery.base_hash: "DEDE52D710DFA7B86AE380E7590F34A7..." surgery.modifications: [{"type": "graft", "source": "qwen3-14b", "layers": "L18:L26"}] surgery.author: "jordan@firesidelabs.ai" surgery.timestamp: "2026-04-15T10:23:00Z"

This enables provenance tracking, lineage audits, and reproducible model modifications.
