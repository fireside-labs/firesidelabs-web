Do You Actually Need a Cloud API? — v2

Do You Actually Need a Cloud API?

Tool-Calling Benchmark v2: 23 Models, Three Providers, One New Failure Taxonomy

Five findings lead this update.

Local Gemma matches cloud Pro tier. Gemma 4 31B-it scores 95 Strict / 96 Adjusted—statistically indistinguishable from Gemini 3.0 Pro (93/97) and Gemini 3.1 Pro (93/96) at 99% confidence. A model that runs on commodity on-prem hardware is inside the confidence interval of Google's top-of-catalog cloud offerings.

Anthropic Haiku 4.5 matches Opus 4.7 on Adjusted score—at one-fifth the price. Claude Haiku 4.5 ($1/1M input) and Claude Opus 4.7 ($5/1M input) both achieve an Adjusted score of 98/100, the highest mark in the entire benchmark. The 5× cost gap between Anthropic's smallest and largest models buys no measurable accuracy on tool-calling workloads.

GPT-5.5-pro provides no measurable value over GPT-5.5 base. The pro variant matches GPT-5.5 base on Strict (88 vs. 88) and trails it slightly on Adjusted (91 vs. 94). At a price premium, there is no accuracy justification for the upgrade on tool-calling workloads.

Type A vs. Type B classification reveals models' real failure modes. When a model fails to call a tool, the failure is not always a miss—it is sometimes a clarifying question. The Adjusted score separates the two. Anthropic's entire lineup shows near-zero Type A failures; OpenAI's GPT-5 family shows 8–10 genuine misses per model. The Strict leaderboard obscures this difference. The Adjusted leaderboard surfaces it.

The newest Gemini Flash didn't move the needle on tool-calling. Gemini 3.5 Flash (89/91) lands within Wilson CI of Gemini 3.0 Flash (86/90)—a 1.5-generation gap that delivers no statistically distinguishable improvement on this workload. Generation-over-generation Flash-tier upgrades are not a substitute for benchmark validation.

"A 20-GB local model beats every cloud model in the benchmark on raw Strict accuracy. The cloud premium buys you no measurable lift on tool-calling workloads, in any tier, at any provider."

2. What Changed Since v1

v1 covered 11 models, all local or Google cloud, with a single accuracy score. v2 makes three structural changes.

Expanded model coverage

The benchmark grew from 11 to 23 models across four architecture families: local Gemma 4 and Qwen3/3.6 variants, Google Gemini (7 models spanning two generations), Anthropic (Opus 4.7, Sonnet 4.6, Haiku 4.5), and OpenAI (GPT-5 family + GPT-5.5 series). This is the first Fireside Labs tool-calling benchmark to cover all three major cloud API providers simultaneously.

Known methodology biases—stated explicitly

The benchmark uses 100 handcrafted tasks across four categories. The distribution is intentionally not flat:

Category Task Count Expected Response
Routing ~60 Tool call
Reasoning ~20 Tool call
Anti-hallucination ~10 None (no tool appropriate)
Ambiguous ~10 None or clarification

Approximately 80% of tasks expect a tool call. This biases the benchmark toward models that call tools aggressively. A model optimized for conservative behavior—asking before acting—will be penalized on Strict even when its behavior is correct. The Adjusted score partially corrects for this. A purpose-built Tool-Calling Judgment Benchmark with a balanced distribution (50/50 tool-expected vs. None-expected) is in development.

Argument validation is key-only, not value-match. A task is marked args_correct if the required argument keys are present in the model's tool call, regardless of argument values. This is a known limitation and is discussed in Section 5.

Temperature is 0 throughout. Single-run per model. No variance measurement across runs.

Type A vs. Type B failure classification

In v1, any "None" response where a tool call was expected counted as a failure, period. v2 re-classifies those failures.

When a model returns no tool call on a task where one was expected, the raw response text is inspected:

Type A — Genuine Miss
Silent failure

The model produced no tool call and no meaningful question. It failed silently, answered in prose, or hallucinated an answer. This is an unambiguous error.

Type B — Clarifying Question
Reasonable abstention

The model produced no tool call because it asked for missing information it genuinely needs—a date, a recipient, a specific value—before committing to an action. Type B responses are credited in the Adjusted score. A model that asks "What date should I schedule this for?" before calling schedule_meeting has not failed—it has correctly identified that the task underspecified a required argument.

Classification uses a regex-based detector: presence of a question mark (?), or phrases matching patterns like "could you clarify", "which one", "what is the", "please provide", and related variants. All "None" responses across all 23 models were re-classified via this detector and stored in per-model *_nones.json files.

3. Three Provider Philosophies

The cross-provider pattern is not random noise. Each provider's lineup shows a consistent behavioral signature.

Anthropic—conservative by design

All three Anthropic models show near-zero Type A failures. When an Anthropic model declines to call a tool, it is almost always asking a question, not silently failing. Haiku 4.5's 20 Type B responses—the most of any model in the benchmark—represent a deliberate posture: it will not guess at a missing email address or an unspecified date. It asks.

Google—balanced routing with generation spread

Google's models show mixed Type A/Type B behavior with no single dominant pattern, but they produce the best raw Strict scores in the upper tier. The generation gap within Google's lineup is the sharpest finding in the dataset: Gemini 2.5 Flash scores 80 Strict; Gemini 3.0 Pro scores 93 Strict—a 13-point gap on the same provider. Teams that have not pinned or validated their Gemini model version may be operating at any point in this 13-point window without knowing it. The newest Flash release (3.5) lands at 89/91—within Wilson CI of 3.0 Flash (86/90) and below 3.1 Flash-Lite (92/93). Generation-over-generation improvement on tool-calling within the Flash tier is below the noise floor of this benchmark.

OpenAI—scattered, with real misses in the base models

OpenAI's lineup is the only provider group with substantial Type A failures across multiple models. GPT-5, mini, and nano each log 8–10 genuine misses—tasks where the model produced no tool call and no meaningful question. These are not clarifications. They are failures. The Adjusted score improves these models substantially because they also ask frequently (17–24 Type B), but the Type A floor represents unrecoverable failures in any pipeline.

5. Future Work

This benchmark is a production instrument, not an academic paper, and its limitations are operational rather than theoretical.

Limitation 01
80% tool-expected distribution is a known bias

This benchmark was designed to stress-test routing accuracy, not to balance the full space of "should I call a tool?" judgments. Models optimized for conservative behavior are penalized in Strict even when that behavior is correct. A successor benchmark—the Fireside Labs Tool-Calling Judgment Benchmark—will use a balanced distribution (50% tool-expected, 50% None-expected) to measure both triggering precision and abstention accuracy. This will also allow proper measurement of anti-hallucination performance, currently underweighted.

Limitation 02
Per-task variance is not measured

Every model was run once per task at temperature 0. Temperature-0 inference is not fully deterministic for all providers, particularly cloud APIs that may apply sampling post-temperature. Multi-run variance measurement is a planned addition for v3.

Limitation 03
Argument validation is key-only

Scoring marks args_correct for presence of required argument keys, not argument values. A future strict-mode scoring pass would validate argument values against expected outputs. This would likely lower Strict scores for all models, but ranking order is not expected to change materially for top-tier models—their failures are primarily routing failures, not argument-value failures.

Limitation 04
Type B classification is regex-based

The clarification detector looks for question marks and specific phrases. It does not use a model judge. Edge cases exist—a model that produces a rhetorical question, or a question about a topic unrelated to the missing argument, will be mis-classified as Type B. Manual review of a random sample of Type B classifications found no systematic errors in this dataset, but the detector is not guaranteed to generalize to new task distributions.
